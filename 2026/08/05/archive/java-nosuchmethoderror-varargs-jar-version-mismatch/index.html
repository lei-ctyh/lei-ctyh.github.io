2. 运行时加载了另一个版本

部署后，类加载器实际加载的是新版本 ContentDAO。新版本删除或替换了旧方法签名，导致调用方 Class 文件记录的方法无法解析。

3. 只有执行到调用点才会暴露

JVM 通常不会在应用启动时提前解析所有业务代码中的每一个方法调用。只有真正执行到 updateSignState() 的目标调用点时，问题才暴露出来。

因此可能出现以下现象：

  • 应用可以正常启动；
  • 签章模块的大部分页面可以正常打开；
  • 查询类功能可以正常使用；
  • 只有执行“撤销合同”时才报错。

七、为什么不直接替换项目环境的 Jar

解决这类问题通常有三种方式。

方案一：统一使用新版 Jar 重新编译和部署

这是最彻底的方案：

  1. 本地编译环境升级到 8.6.1.1-SNAPSHOT。
  2. CI/CD 和所有开发环境使用相同依赖。
  3. 使用新版 Jar 重新编译所有相关代码。
  4. 部署时保证应用中只存在一个确定版本。

优点是从根本上消除编译期和运行期差异。缺点是需要确认新版 Jar 对整个系统的影响，不能只验证当前一个功能。

方案二：将运行环境回退到旧版 Jar

虽然能让当前 Class 文件重新找到 String[] 方法，但项目环境可能已经依赖新版中的其他修复或功能。贸然回退公共基础 Jar，风险通常比修改一处业务调用更高，因此本次没有采用。

方案三：调用两个版本都稳定存在的方法

本次使用的是这个方案，即改为 update(String, List)。

优点是：

  • 修改范围小；
  • 不需要立即替换公共 Jar；
  • 同时兼容当前两个版本；
  • 参数仍然通过占位符绑定，不需要拼接 SQL。

但要注意，这属于兼容性修复。长期治理仍然应该统一编译期和运行期依赖，否则其他发生过签名变化的方法仍可能触发类似问题。

九、NoSuchMethodError 与相似异常的区别

NoSuchMethodError

典型含义：编译时方法存在，运行时加载的类中不存在相同方法签名。

常见原因：

  • Jar 版本不一致；
  • 运行环境存在旧 Jar；
  • 方法参数或返回值发生变化；
  • 类加载顺序导致加载了非预期版本。

NoSuchMethodException

这是受检异常，通常发生在反射调用中：

它表示反射查找失败，和 JVM 链接阶段的 NoSuchMethodError 不是同一类问题。

AbstractMethodError

通常表示接口或父类的方法契约发生变化，但实现类仍是旧版本。例如接口新增抽象方法后，运行时加载了没有实现该方法的旧实现类。

NoClassDefFoundError

表示编译时存在的类在运行时无法加载，或该类此前初始化失败。它和 NoSuchMethodError 一样，都应优先检查运行时依赖和类加载环境。

十、这次问题带来的启示

1. 可变参数也是方法签名的一部分

下面两个声明在调用体验上很相似：

但它们的底层参数分别是 String[] 和 Object[]。将公共 API 从前者修改为后者，即使源码重新编译后仍能调用，也会破坏已经编译好的旧代码的二进制兼容性。

2. “源码兼容”不等于“二进制兼容”

使用新版 Jar 重新编译原源码可能完全正常，这只能说明源码兼容。旧 Class 文件能否不重新编译直接运行，则取决于新版是否继续保留原来的字节码方法描述符。

公共基础库升级时，需要同时考虑：

  • 源码兼容性；
  • 二进制兼容性；
  • 行为兼容性；
  • 部署环境中的类加载顺序。

3. 公共方法签名不要轻易原地替换

如果基础库确实需要把参数从 String… 扩展到 Object…，更稳妥的升级方式是暂时保留旧方法，并在内部转发：

不过，同时保留两个可变参数重载可能导致部分调用出现重载歧义，因此公共 API 设计阶段还需要谨慎评估。对于已经发布的基础库，更推荐通过新方法名、明确的集合参数，或者完整的兼容性测试来演进接口。

4. 构建和运行必须使用同一套依赖

最重要的工程措施不是记住某个具体报错，而是消除环境漂移：

  • 不要依赖开发者手工复制 Jar；
  • 构建产物应携带确定版本的依赖；
  • CI 构建和生产部署使用相同依赖来源；
  • 启动时输出核心基础包版本；
  • 升级公共 Jar 后执行完整回归；
  • 清理 Tomcat 缓存、旧部署目录和重复 Jar。

遇到下面这些错误时：

  • 编译环境和运行环境的 Jar 版本是否一致；
  • 异常中的 JVM 方法描述符具体是什么；
  • 运行时 Jar 是否真的包含这个完整签名；

  • 是否只替换了基础 Jar，却没有重新编译业务代码；
  • 公共 API 是否修改过参数类型、返回值或静态属性；
  • 应用重启后是否仍加载旧缓存或旧部署目录；
  • 是否存在两个版本都支持的稳定重载可用于临时兼容。
