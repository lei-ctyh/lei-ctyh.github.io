JVM 通常不会在应用启动时，就提前解析所有业务代码里的每一次方法调用。

七、为什么不直接替换项目环境里的 Jar

这类问题一般有三种解决方式。

方案一：统一使用新版 Jar，重新编译并部署

这是最彻底的做法：

  1. 本地编译环境升级到 8.6.1.1-SNAPSHOT。
  2. CI/CD 和所有开发环境统一使用相同依赖。
  3. 使用新版 Jar 重新编译所有相关代码。
  4. 部署时保证应用里只存在一个确定版本。

好处是可以从根本上消除编译期和运行期的差异。

缺点也很明显：需要确认新版 Jar 对整个系统的影响，不能只验证当前这一个功能。

方案二：把运行环境回退到旧版 Jar

这样确实能让当前 Class 文件重新找到 String[] 版本的方法。

但项目环境可能已经依赖了新版 Jar 里的其他修复或功能。贸然回退公共基础 Jar，风险通常比改一处业务调用更高，所以这次没有这么做。

方案三：调用两个版本里都稳定存在的方法

这次采用的就是这个方案，也就是改用 update(String, List)。

它的优点是：

  • 修改范围比较小；
  • 不需要马上替换公共 Jar；
  • 可以同时兼容当前两个版本；
  • 参数仍然通过占位符绑定，不需要拼接进 SQL。

不过要注意，这只能算一次兼容性修复。

从长期来看，还是应该统一编译期和运行期依赖。否则其他发生过签名变化的方法，之后仍然可能触发类似问题。

九、NoSuchMethodError 和几个相似异常有什么区别

NoSuchMethodError

典型情况是：编译时方法存在，但运行时加载的类里没有相同的方法签名。

常见原因包括：

  • Jar 版本不一致；
  • 运行环境里残留了旧 Jar；
  • 方法参数或返回值发生了变化；
  • 类加载顺序导致加载了非预期版本。

NoSuchMethodException

这是一个受检异常，通常出现在反射调用里：

它表示反射查找方法失败，和 JVM 链接阶段抛出的 NoSuchMethodError 不是一回事。

AbstractMethodError

通常表示接口或父类的方法契约发生了变化，但实现类还是旧版本。

例如接口新增了一个抽象方法，运行时却加载了一个没有实现该方法的旧实现类。

NoClassDefFoundError

表示编译时存在的类，在运行时无法加载，或者这个类之前初始化失败了。

它和 NoSuchMethodError 一样，都应该优先检查运行时依赖和类加载环境。

十、这次问题带来的几个启示

1. 可变参数也是方法签名的一部分

下面两个声明看起来很像：

调用方式也差不多，但它们底层的参数类型分别是 String[] 和 Object[]。

把公共 API 从前者直接改成后者，就算原源码用新版 Jar 重新编译后还能正常调用，也会破坏已经编译好的旧代码的二进制兼容性。

2. “源码兼容”不等于“二进制兼容”

使用新版 Jar 重新编译原来的源码，如果一切正常，只能说明源码兼容。

旧 Class 文件能不能不重新编译，直接放到新环境里运行，要看新版是否还保留了旧的字节码方法描述符。

升级公共基础库时，最好同时考虑：

  • 源码兼容性；
  • 二进制兼容性；
  • 行为兼容性；
  • 部署环境里的类加载顺序。

3. 公共方法签名不要轻易原地替换

如果基础库确实需要把参数从 String… 扩展成 Object…，更稳妥的方式是先保留旧方法，再在内部转发：

不过，同时保留两个可变参数重载，也可能让部分调用出现重载歧义，所以公共 API 的设计还是要谨慎评估。

对于已经发布的基础库，更推荐通过新方法名、明确的集合参数，或者完整的兼容性测试来演进接口。

4. 构建和运行必须使用同一套依赖

最重要的工程措施，不是记住这次具体报了什么错，而是尽量消除环境漂移：

  • 不要依赖开发者手工复制 Jar；
  • 构建产物应该带上确定版本的依赖；
  • CI 构建和生产部署使用相同的依赖来源；
  • 启动时输出核心基础包版本；
  • 升级公共 Jar 后做完整回归；
  • 清理 Tomcat 缓存、旧部署目录和重复 Jar。

十一、排查清单

遇到下面这些错误时：

可以快速检查：

  • 编译环境和运行环境的 Jar 版本是否一致；
  • 异常里的 JVM 方法描述符具体是什么；
  • 运行时 Jar 是否真的包含这个完整签名；
  • 是否同时存在多个包含相同类的 Jar；
  • Tomcat 公共 lib 是否覆盖了应用里的 WEB-INF/lib；
  • 是否只替换了业务 Class，却没有同步基础 Jar；
  • 是否只替换了基础 Jar，却没有重新编译业务代码；
  • 公共 API 是否修改过参数类型、返回值或静态属性；
  • 应用重启后是否仍然加载了旧缓存或旧部署目录；
  • 是否存在两个版本都支持的稳定重载，可以先做临时兼容。
